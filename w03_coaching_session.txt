Without it, unhandled rejections or runtime exceptions will either crash your entire Node process or leave incoming HTTP requests hanging indefinitely until they time out.

### Why You Need It

* **Crash Prevention:** An unhandled promise rejection or throw in an asynchronous task can terminate your server process.
* **Consistent Client Responses:** Ensures clients receive a structured JSON error response (e.g., status `500` with an error message) instead of an abrupt connection close or timeout.
* **Security & Observability:** It lets you log full stack traces internally while sanitizing details sent to users, preventing sensitive server internals or database queries from leaking.

---

### Where It Belongs: Controller vs. Middleware

**It should not live inside `controllers/errors.js`.** 

Controllers handle route-specific business logic. Global error management operates across the entire application lifecycle and is split into two layers:

1. **Express Centralized Error Middleware:** Belongs in `middleware/errorHandler.js` (or similar).
2. **Process-Level Guards:** Belongs in your entry point (`server.js` or `app.js`).

---

### Implementation in an Existing Codebase

#### 1. Define the Centralized Error Middleware

Create `middleware/errorHandler.js`:

```javascript
// middleware/errorHandler.js
const errorHandler = (err, req, res, next) => {
  const statusCode = err.statusCode || 500;
  
  // Log the error internally for debugging
  console.error(`[Error] ${req.method} ${req.url}:`, err.stack || err.message);

  res.status(statusCode).json({
    success: false,
    message: err.message || 'Internal Server Error',
    // Exclude stack trace in production environments
    ...(process.env.NODE_ENV !== 'production' && { stack: err.stack }),
  });
};

module.exports = errorHandler;
